# Cursor / AI 上下文使用指南

## 1. 目标

不要让 AI 每次都读取整个项目和全部架构文档。

目标：

“最少必要上下文 + 足够完整理解”。

长期架构文档用于复杂任务。

普通任务优先读取当前模块和直接依赖。

---

## 2. 所有任务默认读取

Cursor 项目 Rule 会始终提供：

.cursor/rules/dsh-core.mdc

因此普通任务不需要重复加载全部架构文档。

---

## 3. 简单任务

例如：

- 文案
- 小 CSS
- 明确的小 Bug
- 单一函数修复
- 简单测试修复
- 很局部的 UI 调整

读取：

1. 当前文件
2. 直接调用者/被调用者
3. 对应测试
4. 必要的类型定义

通常不需要加载完整架构文档。

---

## 4. 普通功能开发

读取顺序：

1. 搜索已有类似实现
2. 当前入口
3. 相关调用链
4. 状态来源
5. 相关公共组件 / Service / Store
6. 对应测试
7. 如涉及公共与专属边界，再读取 data-source-architecture.md

---

## 5. 新增数据源

必须读取：

1. docs/data-source-architecture.md
2. docs/development-guidelines.md
3. docs/datasource/README.md
4. 相关现有数据源实现
5. 当前数据源自己的文档
6. 当前实施 plan
7. 实际入口和调用链

先确定：

哪些直接复用公共底座。

哪些是真实数据源差异。

禁止先复制一个现有数据源再大面积修改。

---

## 6. 公共底座修改

必须读取：

1. data-source-architecture.md
2. development-guidelines.md
3. 当前公共实现
4. 至少两个不同类型的数据源使用方
5. 测试
6. 当前相关 plan

原因：

修改公共能力必须确认它是真正公共，而不是只为某一个数据源方便。

---

## 7. 架构 / 大重构

建议使用高推理模型。

读取：

1. 核心 Rule
2. data-source-architecture.md
3. development-guidelines.md
4. 当前 plan
5. 相关目录和调用链
6. 测试
7. 必要的历史实现

先分析，再给计划，不直接修改。

---

## 8. 执行既定计划

计划已经由高推理模型确认时：

执行模型主要读取：

1. 当前 plan
2. 当前阶段涉及文件
3. 直接调用链
4. 对应测试
5. 必要的架构文档章节

不需要每一步重新全仓架构设计。

实际代码与计划明显冲突时停止强行执行，重新分析。

---

## 9. Code Review

Review 应重点读取：

- git diff
- 修改文件
- 修改文件直接调用链
- 相关测试
- 原始需求
- 当前 plan

大型公共改动再补：

- architecture
- development-guidelines

优先 Review 实际变化，而不是重复扫描整个项目。

---

## 10. 上下文优先级

一般优先级：

真实代码
>
当前需求
>
当前调用链
>
git diff
>
测试结果
>
当前实施计划
>
详细架构文档
>
历史说明

不要为了文档完整而挤掉真正相关代码。

---

## 11. 上下文质量判断

如果完成一个小功能需要读取：

- 大量不相关目录
- 多套重复实现
- 多个状态源
- 大量 sourceType 分支

说明可能存在架构问题。

应将降低未来 AI 和人工阅读成本作为重构价值之一。

## 当前新增源阅读入口

新增数据源先阅读 data-source-onboarding.md，并核对当前模块类型、Kafka 模块和对应测试。历史计划用于追踪决策，当前实现以接入指南、架构说明和代码为准。
