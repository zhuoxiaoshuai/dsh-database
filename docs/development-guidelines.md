# DSH 长期开发准则

## 1. 先读后写

任何需求开始前先搜索：

- 已有实现
- 调用入口
- 调用链
- 状态来源
- 公共组件
- Store
- Service
- Hook
- Utils
- 相似数据源实现

不能因为创建新文件最快，就绕过现有能力重新开发。

---

## 2. 积极抽象真实重复

项目明确鼓励主动抽象已经存在并得到验证的稳定共性。

如果两个实现：

- 流程基本相同
- UI 基本相同
- 状态基本相同
- 生命周期基本相同
- 只有少量行为不同

则优先：

公共实现 + 明确差异扩展点。

禁止：

复制约 80% → 修改约 20% → 长期维护两套。

80% 不是精确统计值，而是工程判断。

---

## 3. 重复不仅是代码

以下都属于需要检查的重复：

- 业务流程
- UI
- CSS
- 交互
- 状态
- 生命周期
- 校验
- 权限
- 错误处理
- Loading
- History
- AI 协作
- 人工接管
- Knowledge 流程
- 连接流程
- 结果外围
- 常量和产品列表

即使代码文本不同，只要表达同一个稳定业务概念，也需要判断能否统一。

---

## 4. DRY / KISS / YAGNI 一起使用

DRY：

已经存在的稳定重复应收敛。

KISS：

使用满足当前需求的最简单清晰设计。

YAGNI：

不要为尚未出现的假想未来建立复杂框架。

三者不是互相替代。

“复制一套比较简单”不是 KISS。

“以后可能需要”也不足以支持复杂抽象。

判断标准：

真实重复 → 抽。
真实变化 → 留扩展点。
假想未来 → 暂不实现。

---

## 5. 单一事实来源

同一个可变业务事实只保留一个权威来源。

允许：

权威状态 → 派生状态 / 只读投影。

避免：

Workspace 一份
Store 一份
Hook 一份
DataSource 一份
AI 模块再一份

然后通过 Event / useEffect 相互同步。

重点关注：

- 当前连接
- 当前文档
- AI / 人工控制权
- 当前 revision
- 执行状态
- 当前结果
- 当前选中对象

---

## 6. 不建立第二套系统

已有能力可以扩展时，不新增：

- 第二套 Workspace
- 第二套 Execution Store
- 第二套 History
- 第二套 Knowledge
- 第二套 AI Query
- 第二套连接管理
- 第二套公共状态体系
- 第二套公共事件体系
- 第二套公共 Result Frame

只有业务语义本质不同，才允许独立体系。

“单独写更快”不是建立第二套的理由。

---

## 7. 高内聚、低耦合

一个模块内部内容应该高度相关。

普通功能变更尽量局部化。

如果一个很小的需求必须同时修改大量无关模块，应先检查职责边界。

理想状态：

修改 Kafka 不需要理解完整 MySQL 实现。

修改 Result Viewer 不需要理解凭据存储。

修改 Knowledge 公共流程不需要理解 Driver。

---

## 8. 单一职责

一个 File / Class / Service / Hook / Component 应有明确职责。

出现以下情况需要重新拆分：

- 文件职责无法一句话描述
- Connection、Execution、AI、UI 混在一起
- 修改任何功能都需要改同一个 Service
- 大量不相关 import
- 大量数据源类型判断
- 必须读完整个巨型文件才能理解一个局部功能

拆分依据是职责，不是机械行数。

---

## 9. 避免 God File / God Service

不要让少数文件逐渐成为所有功能的中心。

如果某文件：

- 什么需求都需要改
- 什么模块都依赖
- 什么状态都管理
- 什么类型都判断

说明职责已经失控。

---

## 10. 避免 Utils 垃圾场

不要不断向：

utils
common
helpers
misc
base
manager

中加入无关代码。

公共代码也应该有明确领域：

connection
execution
result
knowledge
document
workspace

---

## 11. 优先组合

优先使用清晰的小能力组合。

避免深继承：

Base
→ Abstract
→ Executable
→ Queryable
→ Structured
→ SQL
→ MySQL

继承层级越深，隐藏行为和修改连锁越严重。

---

## 12. 避免万能接口

公共 Interface 只描述真实共同语义。

如果接口逐渐包含：

executeSql
scanRedis
peekKafka
searchElastic
transaction
topic
schema
key

说明已经失去公共意义。

---

## 13. 避免 Optional / Boolean 地狱

警惕：

sql?
redisCommand?
topic?
partition?
schema?
index?
key?

以及：

isSql
isRedis
isKafka
isAi
isReadonly
isStreaming

大量组合。

这通常表示多个不同业务概念被错误塞进同一个模型或入口。

---

## 14. 避免 sourceType 分支泛滥

少量根级注册和分派可以存在。

但公共业务流程中如果大量出现：

if sourceType === ...
switch sourceType ...

应该停止继续加分支并重新检查架构。

尤其关注：

- Workspace
- AI
- History
- Knowledge
- Execution 公共层
- 公共状态
- Result 生命周期

---

## 15. UI / CSS / 交互也是公共资产

不能只抽后端。

相同的：

- Button
- Toolbar
- Tabs
- Drawer
- Dialog
- Panel
- Form 外围
- Loading
- Error
- Empty
- History
- Status
- Result Frame
- AI Pane

优先公共化。

不要复制 JSX / CSS 后只修改少数文字或数据。

---

## 16. 保持调用链直接

每一层必须有明确职责，例如：

- 权限
- 生命周期
- 状态
- 协议转换
- 数据源适配
- 持久化

如果某层长期只是：

return next.sameThing(args)

且没有独立职责，检查是否应删除。

---

## 17. 少用隐式控制流

核心业务优先显式调用。

谨慎使用：

- EventBus
- 全局可变状态
- 隐式注册
- 动态魔法
- 初始化副作用
- 多层事件转发

事件适用于真正的一对多通知，不用于隐藏正常业务调用链。

---

## 18. 明确依赖

一个模块需要什么，应从：

- 参数
- 接口
- Import
- 明确注册

中看出来。

避免依赖：

- 页面是否曾打开
- 某代码是否提前执行
- 隐式全局变量
- 不可见单例副作用
- 特定初始化顺序

---

## 19. Fail Fast

非法：

- 配置
- 输入
- 状态
- 权限

应尽早识别。

不要：

- 猜测
- 自动忽略
- 隐式降级
- 把失败伪装为空结果
- catch 后继续执行

明确区分：

- Failure
- Cancel
- Timeout
- Empty
- Partial Result

---

## 20. 重构保持行为

重构默认只调整内部结构。

除非任务明确要求，否则不能无意改变：

- 功能
- 性能
- 权限
- 安全
- 数据
- 用户体验
- 原有交互习惯

架构更漂亮不能成为回归理由。

---

## 21. 重构流程

公共化或去重复按：

新公共实现
→ 接入一个现有调用
→ 验证
→ 迁移其余调用
→ 回归
→ 搜索旧引用
→ 删除重复旧实现

不要先删除大片稳定代码后重新实现。

也不要新旧两套永久并存。

---

## 22. 删除无效代码

确认：

- 无真实调用
- 无动态加载
- 无测试依赖
- 无兼容职责

后应删除。

不要因为“未来也许有用”永久保留。

版本控制负责保存历史。

---

## 23. 兼容层必须有理由

兼容代码必须能够回答：

- 为什么存在
- 谁还在调用
- 删除条件是什么

避免：

legacy
legacy2
new
new2
compat
temporary

长期堆积。

---

## 24. 设计模式不是目标

Factory、Strategy、Provider、Registry、Observer 等只在解决真实问题时使用。

每新增一个：

- Interface
- Service
- Factory
- Provider
- Registry
- Hook
- Store
- Adapter

都要能说明它实际解决了什么问题。

---

## 25. 可读性优先

代码优先：

- 显式
- 可搜索
- 易跳转
- 易追踪
- 命名清楚

避免：

- 过度元编程
- 极端泛型
- 隐藏控制流
- 为减少几行代码制造难理解机制

代码是给未来人和 AI 阅读的。

---

## 26. AI 阅读成本

AI 阅读成本属于架构质量指标。

理想情况：

理解公共流程 → 阅读公共核心。

理解某数据源 → 公共核心 + 该数据源模块。

不应该：

为了理解一个普通功能，需要扫描几十个重复文件、比较多套 Store、猜测哪个状态是真的。

---

## 27. 开发完成后的固定 Review

每次完成修改后检查：

### 重复
- 重复代码
- 重复流程
- 重复 UI
- 重复 CSS
- 重复交互
- 重复状态
- 重复业务规则

### 复杂化
- 过度设计
- 无意义抽象
- 无意义 Wrapper
- 调用链过深
- 深继承
- 巨型接口

### 架构
- 公共逻辑是否落入专属模块
- 专属逻辑是否泄漏公共层
- sourceType 分支是否增加
- 是否建立第二套系统

### 状态
- 是否新增第二份权威状态
- 是否产生大量同步代码
- 是否出现隐式副作用

### 清理
- 死代码
- 废弃入口
- 可删除兼容代码
- 已被公共能力替代的旧实现

---

## 28. 优先级

发生取舍时：

功能正确
>
兼容现有行为
>
安全与权限
>
减少重复
>
架构边界
>
可读性
>
可维护性
>
形式上的漂亮

长期目标：

系统功能越来越多，但理解成本不能同比增长。
